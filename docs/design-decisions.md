# Design decisions, schema and rationale

The full design log for the KR Capital watchlist: what was decided, what was tried and replaced, and
why. The short version, with run instructions, is in the [README](../README.md).

---

A market watchlist and basic security screener for the S&P 100: daily price history, versioned reference
data with an audit trail, baskets and mock portfolios, and return analytics. The repo contains the
backend (API, ETL, scheduler) and the React frontend.

## Running it

Requirements: Docker, and a free [Polygon.io](https://polygon.io) API key for live data.

```bash
cp .env.example .env          # add POLYGON_API_KEY
docker compose up --build
```

- `migrate` applies database migrations, then `etl` bootstraps the data: it restores the committed seed
  snapshot if one is present, otherwise runs a full live load (~40 min on the free Polygon tier), then
  tops up the days missing since the snapshot (one call per missing day, usually a minute or two).
  The API is usable throughout.
- `api` serves on http://localhost:8000 (interactive docs at http://localhost:8000/docs).
- `scheduler` runs the nightly jobs (Tuesday to Saturday, 06:00 New York time).

Useful commands:

```bash
docker compose run --rm etl python -m app.etl load        # full live load
docker compose run --rm etl python -m app.etl prices      # full price refresh (nightly job)
docker compose run --rm etl python -m app.etl topup       # fetch only the days missing since the last bar
docker compose run --rm etl python -m app.etl reference   # refresh reference data (new versions)
docker compose run --rm etl python -m app.etl dump-seed   # write seed/ snapshot from the current DB
```

Polygon is the only data source. Without `POLYGON_API_KEY` the app serves the committed seed snapshot
but cannot fetch anything new. Regenerate the snapshot with `dump-seed` after a fresh `topup`.

API overview (full spec in `backend/openapi.json`, or the interactive docs at `/docs`). Stocks are
addressed by their current ticker:

| Endpoint | Purpose |
|---|---|
| `GET /instruments` | Grid rows: last close, 1D/1M/YTD return, market cap |
| `GET /instruments/{ticker}` | Current identifiers and details |
| `GET /instruments/{ticker}/prices?start&end&mode=price\|daily\|cumulative&as_of` | Split-adjusted closes or price returns; missing days are fetched and stored first (unless `as_of` is given) |
| `GET /instruments/{ticker}/versions?as_of=` | Reference-data history, oldest first ("as was" with `as_of`) |
| `GET/POST /instruments/{ticker}/annotations`, `PATCH/DELETE …/annotations/{id}` | Annotations; the author can edit or delete their own |
| `GET/POST /baskets`, `GET/DELETE /baskets/{id}`, `POST /baskets/{id}/members`, `DELETE /baskets/{id}/members/{ticker}` | Baskets: named groups of stocks, optionally with target quantities |
| `GET /baskets/{id}/returns?start&end&as_of` | Portfolio value and returns, when every member has a target quantity |
| `GET /jobs`, `GET /health` | ETL run history, health check |

Tests (need Postgres from `docker compose up db`):

```bash
cd backend && uv sync && uv run pytest
```

## Data schema (Postgres)

`instrument_id` is a UUID generated by the app. There is no table of instruments: every table that
refers to a stock stores its UUID, without a foreign key; the API checks it exists before writing.
Every id in the schema is a UUID.

### Reference layer

`instrument_metadata`: each stock's identifiers and details. Insert-only: a change adds a new row.
| column | type | constraints |
|---|---|---|
| instrument_id | UUID | the stock's stable id |
| ticker | TEXT | NULL = ticker taken over by another stock |
| figi | TEXT | composite FIGI |
| name | TEXT | NOT NULL |
| sic_code | TEXT | NULL |
| sic_description | TEXT | NULL |
| primary_exchange | TEXT | NULL (MIC code) |
| currency | VARCHAR(3) | NOT NULL |
| shares_outstanding | BIGINT | NULL, CHECK > 0 |
| listing_status | VARCHAR(16) | CHECK IN ('ACTIVE','DELISTED') |
| data_version | TIMESTAMPTZ | NOT NULL; when we recorded this row |
- PK (instrument_id, data_version); INDEX (ticker), INDEX (figi)
- EXCLUDE USING gist (figi WITH =, instrument_id WITH <>): a FIGI can appear in any number of versions
  of one stock, but never under two different `instrument_id`s. Tickers can't be constrained the same
  way, since they are legitimately reused by other companies over time.
- "As is" = the latest row per instrument; "as was" at time T = the latest row with `data_version <= T`
- What changed = the fields that differ between consecutive rows of the same instrument

### Market data layer

`instrument_daily_price`: daily bars, versioned like `instrument_metadata`. Insert-only.
| column | type | constraints |
|---|---|---|
| instrument_id | UUID | |
| trade_date | DATE | the trading day the bar is for |
| data_version | TIMESTAMPTZ | when we recorded this version of the bar |
| open, high, low, close | NUMERIC(18,6) | split-adjusted; NOT NULL, CHECK > 0, CHECK high >= low |
| volume | BIGINT | NOT NULL, CHECK >= 0 |
- PK (instrument_id, trade_date, data_version)
- A new version is stored only when Polygon's bar for that day changes; the latest version per
  (instrument_id, trade_date) is current

### User / workspace layer

`basket`
| column | type | constraints |
|---|---|---|
| id | UUID | PK, DEFAULT gen_random_uuid() |
| name | TEXT | NOT NULL |
| created_by | TEXT | NOT NULL |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |
- UNIQUE (created_by, name)

`basket_member`
| column | type | constraints |
|---|---|---|
| basket_id | UUID | FK → basket ON DELETE CASCADE |
| instrument_id | UUID | |
| target_quantity | NUMERIC(18,4) | NULL; optional, but portfolio returns need it on every member |
| added_by | TEXT | NOT NULL |
| added_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |
- PK (basket_id, instrument_id); removal = hard DELETE

`annotation`: editable and deletable by its author.
| column | type | constraints |
|---|---|---|
| id | UUID | PK, DEFAULT gen_random_uuid() |
| instrument_id | UUID | NOT NULL |
| author | TEXT | NOT NULL |
| body | TEXT | NOT NULL, CHECK length(body) > 0 |
| annotation_date | DATE | NULL; optional day the annotation is about |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() |
| edited_at | TIMESTAMPTZ | NULL; set when the author edits the annotation |
- INDEX (instrument_id, created_at)

### Operations

`job_run`
| column | type | constraints |
|---|---|---|
| id | UUID | PK, DEFAULT gen_random_uuid() |
| job | VARCHAR(32) | NOT NULL (`load`, `prices`, `topup`, `reference`, `restore-seed`) |
| params | JSONB | NULL |
| status | VARCHAR(16) | CHECK IN ('RUNNING','SUCCEEDED','FAILED') |
| started_at | TIMESTAMPTZ | NOT NULL |
| finished_at | TIMESTAMPTZ | NULL |
| rows_written | INT | NULL |
| error | TEXT | NULL |

`instrument_snapshot`: a regular (not materialized) view that feeds the grid, computed on every read.
Columns: instrument_id, ticker, name, sic_description, last_trade_date, last_close, ret_1d, ret_1m,
ret_ytd, market_cap (last close × current shares_outstanding).

## Design decisions

### Upstream rate limits (checked 2026-10-12) and how they shaped the design
| Source | Free-tier limit | Used? |
|--------|-----------------|-------|
| Polygon.io (now branded Massive) – Stocks Basic | 5 API calls / minute; 2 years of history; end-of-day data only | Yes, the only source |
| OpenFIGI mapping | 25 requests / minute without a key | No: Polygon's ticker details already include the composite FIGI |
| yfinance | No published limit; unofficial Yahoo Finance client that can be throttled without notice | No |

Load cost for the S&P 100 (101 tickers, since GOOGL/GOOG are both included): one reference-data call plus
one 2-year daily-bars call per ticker is ~200 Polygon calls, about **40 minutes** at 5/minute. For the
S&P 500 the same load would be ~1,000 calls, about **3.3 hours**.

These numbers drove several decisions below: the universe is capped at the S&P 100; data is preloaded
once and stored permanently; startup only fetches the days missing since the seed snapshot, using
Polygon's grouped-daily endpoint (one call returns every stock's bar for a day); users cannot add
arbitrary tickers, since each would cost Polygon calls during use; and the full refresh runs once a
night, early in the morning, when nobody is waiting on it, because the free Polygon tier is end-of-day
only and releases a day's bars after midnight.

### Universe: S&P 100
The app tracks a fixed universe of the S&P 100 constituents. The main constraint is upstream API
query limits on free tiers and the cost of an initial load: every instrument needs reference data and
~2 years of daily prices, so the number of names directly drives load time and rate-limit exposure. The
S&P 100 is large enough for screening to be meaningful (cross-sector comparisons, recognizable
mega-caps) while keeping the initial load small. Alternatives considered: a full index like the S&P 500
(a richer screener, but ~5× the API calls and load time), or letting users choose their own tickers (no
fixed load cost, but the screener only covers names someone has already added, and a new ticker has no
history until it is fetched).

### Data loading: hybrid ETL + on-the-fly
A one-off, re-runnable ETL job preloads prices and reference data for all S&P 100 names, so the
screener has a complete universe the moment the app opens. After that, data is sourced on the fly:
missing date ranges and reference-data refreshes are fetched when needed and stored permanently rather
than cached and discarded. Pure ETL was rejected because nothing new appears until the next job run;
pure on-the-fly was rejected because the screener would be empty until each name had been viewed, and
there would be no stored history to detect reference-data changes against. Users cannot add tickers
outside the S&P 100 in this version, which keeps load and rate-limit behaviour predictable.

### One data source: Polygon
The brief suggests several public sources (yfinance, OpenFIGI, Polygon). The app deliberately uses only
Polygon: its ticker-details endpoint returns the ticker, composite FIGI, name, SIC industry and shares
outstanding in one call, and its daily-bars endpoints cover price history. One source means one client,
one key, one rate limit and one set of response shapes to test, and no mismatches between sources
(rounding, adjustment rules, ticker spellings such as BRK.B vs BRK-B vs BRK/B). Polygon was chosen over
yfinance as the single source because it is an official API and supplies FIGIs, which make ticker
renames safe.

A multi-source design was built first and then removed: OpenFIGI for identifiers, Polygon for reference
data and prices, and yfinance as a price fallback and for intraday quotes. It added resilience but tripled
the integration surface and needed rules for which source wins. The trade-offs of the single source:
- **No backup:** if Polygon is down or the key is revoked, nothing new arrives. The API keeps serving
  stored data, so the screen goes stale rather than breaking.
- **No live prices:** see "Prices are the previous close" below.

### Prices are the previous close: no live quotes
The app never shows a live or "current" price. Every price is a stored official daily close, and the
grid's "As of" column says which day. The cause is the data plan rather than the app: Polygon's free
tier is end-of-day only, and asking it for the most recent day is refused with an HTTP 403. This was
checked on 2026-10-14 at 23:50 New York time, eight hours after the close: that day's bar was refused,
while the previous day's was served. At 00:06 the same night that day's bar was served and the new
current day was the one refused. The freshest data available is therefore the previous trading day's
close, and fetching on the fly cannot improve on it: the API's on-demand gap fill and the nightly jobs
receive exactly what the plan allows. The grid shows the latest stored close, not today's.

**Schedule.** Because a day's bars appear just after midnight New York time on the next day, the nightly
jobs run at **06:00 ET, Tuesday to Saturday**: before the market opens, each run stores the previous
day's close (Tuesday stores Monday's, ..., Saturday stores Friday's; no Monday run is needed because
Saturday's covers Friday). The first schedule was weekdays at 17:00, on the assumption that the close
is available the same evening. It isn't, so that run could never store the day it had just seen close:
the grid showed Oct 13's close throughout Oct 15's trading hours although Oct 14's was available from
midnight, roughly 11 hours staler than the plan allows. Moving the run gives the freshest data the plan
can serve.

The same assumption broke the startup `topup`, which asks for every trading day up to the last closed
session. Started after 4pm on a trading day it asked for that day's bars, got the 403 and failed with a
traceback, so the Polygon client now reports a 403 as a distinct "not available yet" condition and
`topup` stops at the first such day, keeps everything before it, and finishes successfully; the next run
picks the day up. A genuine outage (5xx, network, bad key) still fails the job.

Options considered for a current price:
1. **A display-only delayed quote from a free source** (e.g. yfinance): shown while the market is open,
   cached for about a minute, never stored, with a fallback to the last close. Rejected: the source is
   unofficial and can break without notice, and it would bring back a second data source, which was
   removed on purpose to keep the system simple.
2. **A paid Polygon plan with intraday data.** The cleanest route (one source, one key), but it costs
   money and the exercise does not need it.
3. **Nothing: show the last close.** Chosen.

The brief asks for historical pricing, reference data and analytics built on them, not live quotes, and
every figure in the app (returns, portfolio values, market cap, 52-week range) is defined on daily
closes, so a live price would sit beside them rather than feed them. The consequences: values are as of
the last stored close; the page loads its data once, so a refresh is needed to see a newly stored day; and
real-time quotes are listed under next steps, with the free plan as the limiting factor.

### First run: committed seed snapshot
A full live load from Polygon takes about 40 minutes on the free tier, which is a poor first experience
for anyone cloning the repo. The repo therefore includes a compressed dump of the reference and price
tables: the first `docker compose up` restores it in seconds, and a "top-up" then fetches only the
trading days missing since the snapshot was taken, with one grouped-daily call per day for all stocks
(about a minute for a week-old snapshot). The API is usable throughout, showing the snapshot's prices
until the top-up finishes. The slower full refresh is left to the nightly job. A full live load from
scratch remains a single command.

The snapshot is committed in `seed/` (about 1.1 MB: 202 metadata rows and 50,542 price rows, taken on
2026-10-15 with closes through 2026-10-14). Restoring it into an empty database with no API key was
tested end to end: 101 instruments, 50,542 prices, a populated grid view and the FIGI constraint in
place. Baskets and annotations are user data and are not part of it. Because the data comes from
Polygon's free plan, whose terms may restrict redistribution, the snapshot is a reason to keep the
repository private or to check those terms before making it public.

### ETL scheduling: cron (Supercronic)
The ETL is a CLI in the backend codebase, sharing models and the Polygon client with the API. A one-shot
docker-compose service runs the initial load, and a small scheduler container runs the same CLI on a
crontab (via Supercronic, a container-friendly cron runner). From Tuesday to Saturday at 06:00 ET it runs
the full price refresh, then refreshes reference data, about 40 minutes in total; the morning slot, rather
than the evening of the close, is because the free plan releases a day's bars after midnight (see "Prices
are the previous close"). Each step is idempotent and records
its run in a `job_run` table, so retries and run history are visible without an orchestrator. Airflow was
considered: it adds per-step retries, backfills and a run UI, but costs several containers and hours of
setup for what is a single daily chain. Vercel Cron was considered too, but it requires a cloud-deployed
backend and hosted database, while this is a local application. Both are the natural upgrade paths once
the app is deployed or the number of jobs grows.

ETL jobs are not prevented from overlapping (e.g. the startup `bootstrap` and a manual `load`). Running
two at once once created a duplicate instrument, which the FIGI exclusion constraint now rules out; the
remaining effects of overlap are a job failing on that constraint, redundant price versions with
identical values, and both jobs sharing Polygon's rate limit. A Postgres advisory lock allowing one job
at a time was considered and left out as not worth the extra moving part for a single-user local app;
it is listed under next steps.

### Instrument identity: a UUID, with ticker and FIGI as versioned fields
Each stock has a UUID that never changes, and everything else (prices, baskets, annotations, reference
history) refers to it. The ticker and FIGI are ordinary fields of `instrument_metadata`, versioned like
the rest, because tickers change and get reused (e.g. FB → META): keying data on the ticker would orphan
it on the first rename. When the ETL fetches a stock it matches it to an existing instrument by FIGI
first, then by current ticker, so a renamed ticker keeps its UUID and the rename shows up in the change
log. If a ticker is reassigned to a different company, the previous holder gets a new row with no
ticker. The API addresses stocks by their current ticker (`/instruments/AAPL`), which is readable and
bookmarkable, and resolves it to the UUID internally.

There is deliberately no separate table of instruments: it would only hold the UUID. The cost is that
other tables can't have database foreign keys to the instrument; the API checks the stock exists before
writing, and only the ETL creates instruments. Share-class FIGIs and SEC CIKs were dropped as unused.

### Database: Postgres
Data is stored permanently in Postgres, run locally via docker-compose. It gives a production-like
setup and the constraint and indexing features the versioned reference data benefits from. SQLite was
considered for its zero-setup simplicity, but it has a weaker production story.

### Backend: FastAPI + SQLAlchemy
The API is FastAPI with SQLAlchemy and Alembic migrations. Typed request/response models produce an
OpenAPI spec that generates TypeScript types for the React frontend, so frontend/backend drift fails the
build. The versioning and audit tables are modeled explicitly rather than delegated to a plugin. Django +
DRF was considered: it offers an admin UI, built-in migrations and management commands, but its audit
plugins would hide the data-model design and its typed-contract story with React is weaker.

### No raw-payload layer
Provider responses are normalized straight into our own tables rather than first stored verbatim. This
keeps storage and code smaller; the cost is that data cannot be rebuilt from stored responses without
re-calling the API, and values cannot be traced back to the exact response they came from. A raw
landing table is a natural addition once there are more sources or debugging upstream changes matters.

### Prices: split-adjusted and versioned
When a company splits its stock (e.g. 1 share at $1,000 becomes 10 shares at $100), raw prices show a
fake crash. Polygon's default daily bars are split-adjusted, so charts and returns stay correct, and we
store only those. A new split changes past adjusted prices, so prices are versioned the same way as
reference data: rows are insert-only, each stamped with `data_version`, and the latest version of each
day's bar is current. The nightly job re-fetches every stock's 2-year history (one call per stock,
about 20 minutes) and stores a new version only for bars whose values changed. On a normal night that is
just the new day; after a split it is the stock's whole rescaled history, while the pre-split versions
are kept. This catches splits and any vendor corrections without a detection heuristic, and keeps an
audit trail of what the app showed at any time. An earlier version overwrote bars in place and detected
splits by re-checking one day's close; it was replaced because it rewrote history.

Returns are price returns and exclude dividends. Storing raw prices alongside, or dividend-adjusted
(total-return) prices, was considered and deferred to keep the model simple. One known limitation:
Polygon's free tier only serves the last two years, so once the app has been running for more than two
years, a split can't produce new versions for bars older than that.

### Reference-data history: one versioned table
Each change to a stock's identifiers or details inserts a new `instrument_metadata` row stamped with
when we learned it (`data_version`); rows are never updated or deleted. The latest row is current ("as
is"), and the latest row at or before any past moment gives "as was". A separate valid-to column was
considered and dropped: with insert-only rows it is redundant, and leaving it out means versions can
never overlap or contradict each other. `data_version` records when we learned a change, not when it
happened in the world; Polygon's reference endpoint doesn't supply real-world effective dates, so
tracking them (full bitemporal history) is listed as a next step.

`data_version` is the start time of the job run that stored the row: each ETL run takes one timestamp
and stamps everything it writes with it, so one nightly run is one version across all stocks. The
`as_of` parameter (on versions, prices and portfolio returns) reads the latest version recorded at or
before a point in time; a plain date such as `2026-10-14` means the end of that day in New York, so
it includes that evening's nightly run. Analysis pinned to one `as_of` therefore sees one consistent
snapshot of the data, even if later runs add new versions. Truncating `data_version` itself to a date
was considered; it reads more simply, but two runs on the same day (e.g. a manual re-run) would collide
and force one to overwrite the other, breaking the insert-only rule.

Reference data is re-fetched nightly, right after the price job. Like the price refresh it needs one call
per instrument, about 20 minutes at 5 calls per minute, which is fine for an overnight batch. Whenever
a fetched record differs from the current row (compared field by field), a new row is written. The
versions themselves are the audit trail, exposed through the versions endpoint: comparing consecutive
versions shows exactly what changed and when. A separate change-log table, and later a "changes"
endpoint computing diffs, were built first and then removed: both only restated what the versions
already show.

Market cap is not stored: it changes every day with the price, so versioning it would create a new
reference version daily and bury meaningful changes such as a new name or ticker. It is calculated on
read as close × shares outstanding.

### Simplifying the schema
The first working version had ten tables and views; a review pass cut it to six tables and one view by
asking, for each table and column, what would break without it. What changed, and why:

- **`instrument`, `instrument_identifier` and `instrument_version` became one `instrument_metadata`
  table.** `instrument` only held an id, and identifiers (ticker, FIGI) change over time just like
  names and industries, so they are now versioned fields of the same row. The stock's id is a UUID that
  other tables store directly; the cost is no database foreign key to "the instrument", which the API
  compensates for by checking the stock exists before writing.
- **The change-log table, and later a `/changes` endpoint, were removed.** Both restated what
  consecutive versions already show. The versions endpoint is the audit trail; the frontend's history
  list compares versions client-side.
- **The metadata row id was dropped.** It only existed so the change log could point at a version. A
  version is identified by `(instrument_id, data_version)`, which is now the primary key, matching how
  `instrument_daily_price` is keyed.
- **`attrs_hash` was dropped.** It was a shortcut for "did anything change?", but change detection
  already loads the current row, so comparing fields directly is just as simple and one column less.
- **`source` was dropped from both versioned tables.** With Polygon as the only source it was always
  `polygon`. It should come back if a second source is added.
- **Every id is a UUID, and columns keep the `id` / `…_id` names.** Baskets, annotations and job runs used
  auto-incrementing integers, while instruments used UUIDs; one id type is simpler to reason about.
  Renaming columns to `uuid` was considered, but naming columns by role rather than type is the common
  convention and lets the type change without renaming.
- **Basket `type` was dropped** (see Baskets below), and **the grid's materialized view became a regular
  view** (see Analytics).
- **Share-class FIGIs and SEC CIKs were dropped** as unused. Handling CIKs had already required a special
  case: one company's CIK is shared by several share classes (GOOG and GOOGL).
- **A uniqueness rule came back in a different form.** Dropping the old "one current holder per
  ticker" index left nothing in the database to stop two concurrent loads from both creating the same
  stock, which is exactly what happened once (two AAPL instruments). Since a composite FIGI identifies
  one security permanently, an exclusion constraint now rejects any row whose FIGI already belongs to a
  different `instrument_id`, while still allowing many versions of the same stock.
- **Kept on purpose:** `sic_code` alongside `sic_description`. Nothing uses it yet, but SIC codes are
  hierarchical (the first two digits are a broad industry group), which is the closest Polygon offers to
  a sector filter, and the code stays stable if the description is reworded. Open/high/low/volume were
  also kept even though only the close is used today: Polygon returns them in the same call, and volume
  is a common screener column.
- **Names:** `price_bar_daily` became `instrument_daily_price`, matching `instrument_metadata`, and the
  versioning column is called `data_version` in both tables (it replaced `recorded_from`/`recorded_to`,
  then `recorded_at`; a separate `effective_date` column was dropped because Polygon never fills it).

### Sector classification: Polygon SIC
Instruments are classified by the SIC industry code Polygon provides, keeping reference data to one
official source. The trade-off is that analysts usually screen by GICS sectors, which SIC does not
match; adding GICS from a public constituent source is listed as a next step.

### Baskets: one model for themes, watchlists and portfolios
Tagging a security into a theme, adding it to a watchlist, and holding it in a mock portfolio are all
"membership of a named group", so they share one `basket` table and one membership table. Members can
carry an optional target quantity; a basket whose members all have one works as a mock portfolio, and
its returns can be computed. An explicit basket type (theme / watchlist / portfolio) was built first
and removed: only the quantities change what the app can do, so the type added a concept and validation
rules without adding behaviour. Separate tables per kind were also considered, but would repeat the same
membership logic. Removing a member deletes the row, so basket history is not kept; this is a
deliberate simplification, unlike reference data, which is fully versioned.

### Users
There is no login. A single configurable mock user id is recorded as the author of every write, so the
data model already supports attribution; real authentication (e.g. SSO) is a next step.

### Universe membership
The S&P 100 list is a fixed seed list, and constituent changes are applied manually. Tracking dated
membership (when a name joined or left the index) is a next step.

### Annotations
Users attach free-text annotations to a stock, shown newest-first on the company card with author and
time. Authors can edit or delete their own annotations (the API answers 403 for anyone else's, and each
one carries a `can_edit` flag so the UI only offers the buttons where they work); an edited annotation
shows "edited <date>". They were first append-only, to preserve the record of what was said, but that made
typos and outdated annotations permanent, and annotations are commentary rather than market data. Unlike
prices and reference data they are therefore not versioned: an edit replaces the text, and delete removes
the row. Deleting asks for an inline Yes/No confirmation rather than a browser popup.

The feature was first called "notes" and was renamed to match the brief's word ("annotate"). Migration
`0005` renamed the table and column in place, so existing rows were kept.

### Analytics
Returns and portfolio returns are computed on request rather than stored. At roughly 100 instruments ×
500 trading days the data is small enough to compute in milliseconds, and computing on read means late
bars or split corrections never leave stale stored results. The grid's numbers (last close, 1-day,
1-month and year-to-date returns, market cap) come from a regular database view, so they are also
computed on every read. A materialized view (stored results, refreshed after each ETL run) was used
first and replaced: it was faster to read but could go stale whenever a refresh was missed, and at this
data size the live query is fast enough. If the grid ever gets slow, switching back is a one-word
change.

A mock portfolio holds fixed quantities: its value each day is the sum of quantity × adjusted close, and
its daily return is the change in that value. Weights therefore drift with prices, as a real held
position would. Holding fixed weights (rebalancing daily) was the simpler alternative but is less
realistic.

### Frontend: a single-screen desk layout
The React app is one screen, as trading-desk tools usually are: the instrument grid is home, selecting a
row shows its price chart below it, double-clicking opens a company card drawer, and baskets live in a
sidebar. Everything is reachable without changing pages. A multi-page app was the simpler alternative
but adds clicks to every workflow.

```
┌──────────────┬───────────────────────────────────────────────┐
│ BASKETS      │  GRID  (ticker · name · last · 1D · 1M · YTD · │
│ + New        │         mkt cap)  sortable, multi-select       │
│ • AI    (4)  ├───────────────────────────────────────────────┤
│ • Book  (2)  │  CHART  [Price | Daily | Cumulative]           │
│              │         [1M 3M YTD 1Y All]                     │
│ ☆/★ in grid  │  cumulative mode overlays the selected rows    │
│ + search box │                                                │
└──────────────┴───────────────────────────────────────────────┘
        double-click a row → company card drawer (right side)
```

**Stack.** Vite, React and TypeScript, with plain CSS (one stylesheet, a dark desk look). The grid is
AG Grid Community, which provides sorting, filtering and row selection without custom code, and charts
use TradingView Lightweight Charts, which is built for financial time series. A hand-rolled table with
a general-purpose chart library (Recharts) was considered: fewer dependencies, but sorting and
time-series handling would have to be written by hand. Tailwind and component libraries (Mantine, MUI)
were considered for styling and skipped as more setup than one screen needs.

**Calling the API.** Plain `fetch` with a small `useFetch` hook (data, loading, error, reload). TanStack
Query was considered for caching and automatic refetching after writes, but for one screen and a handful
of endpoints the hand-written version is short and has no extra concepts. TypeScript types are generated
from the backend's OpenAPI spec (`openapi-typescript`), so a change to the API that the frontend doesn't
match fails the type check. In development, Vite forwards `/api/*` to FastAPI, so no CORS setup is
needed.

**Grid.** Ticker, name, last close, 1-day, 1-month and year-to-date return, and market cap. An earlier
plan kept only ticker, name, last price and 1-day return for readability; the wider set was chosen
because screening by performance and size is the point of the grid, and the API already returns those
fields. Industry and other details are on the company card.

**Chart.** Toggles between split-adjusted price, daily returns and cumulative return over ranges from one
month to everything stored ("All", currently two years, the most the free Polygon tier serves). Ticking stocks in the grid's **Compare** column (or ⌘/Ctrl-clicking rows) charts
them together in every mode. In price mode an axis switch offers:
- **$**: price in USD. The default for one stock.
- **$ log**: price in USD on a logarithmic axis, the default for several stocks. Equal distances are
  equal percentage moves, so a $1,166 stock and a $112 stock compare fairly while the axis still shows
  real prices.
- **YoY %**: year-over-year growth, each day's close against the close one year earlier. It needs a
  year of history before the first point, so it starts later for ranges near the start of the data.

A caption under the chart always states what the axis shows. An earlier version showed several prices
as "% change since the start of the range" using the chart library's percentage scale; it was replaced
because the percentages were easy to misread and duplicated the cumulative-return mode, and because a
log dollar axis keeps real prices visible. Selection is capped at five, since more lines than that is
unreadable: ticking a sixth is undone with a short notice, and there is no "select all" checkbox. The
checkbox column is labelled "Compare" so it isn't confused with the basket ★ column.

**Resizing.** The sidebar's right edge and the boundary above the bottom panel can be dragged. The bottom
panel can't grow past the point where about five grid rows remain, so it never covers the grid (it
re-clamps if the window shrinks). Inside the bottom panel the chart takes whatever height is left
after the header, so when a narrow layout wraps the header onto two lines the chart shrinks rather than
being pushed out of view, and the portfolio's holdings table scrolls instead of stretching the panel.
Sizes last for the current page only; a refresh restores the default
layout. An earlier version remembered them in the browser, which made a layout that had been dragged
into an awkward state stick across refreshes.

**Company card.** Opened from the ⓘ button on every grid row, the "ⓘ Details & annotations" button on the chart,
the Annotations column, or a double-click. Double-click alone was the first version and proved hard to
discover. The card has:
- **Overview**: the company description, website, headquarters, employee count and listing date, all
  from Polygon's ticker-details call (the same call as the rest of the metadata, so no extra API cost),
  versioned like the other fields.
- **Key figures**: last close, market cap, 1-day / YTD / 1-year return and the 52-week range (of daily
  closes), computed from stored prices.
- **Identifiers & classification**: ticker, FIGI, SIC code and industry, exchange, currency, shares
  outstanding, status, and the `data_version` the details come from.
- **History**: what changed between consecutive versions (e.g. "ticker FB → META · 2026-03-01"), which
  makes the "as is / as was" audit trail visible. A field filled in for the first time (as happened when
  the profile fields were added) is grouped into one "Added: …" line, and a reworded description is shown
  as "Description updated" rather than diffed.
- **Annotations**: free text, optionally tied to the date it is about (e.g. an earnings date); edit or delete your own.

**Annotations.** Annotating a security means attaching your own information to it, on top of the market
data: annotations, and grouping stocks under a theme (baskets). Annotations live in the company card,
newest first, and can optionally carry the date they are about (e.g. an earnings date), shown as
"📍 2026-07-30". The grid's Annotations column shows each stock's count and opens the card.

Dated annotations also appear on the price chart as small yellow dots sitting on the line; clicking a dot
opens a popup with the full text, author and date (several annotations on the same day share one dot),
with a button to open the card. Escape or a click elsewhere closes it. A date on a weekend or holiday
moves to the next trading day, and dates outside the plotted range are not drawn. This is the second
version of the idea: the first drew each annotation's text on the chart as a label, which piled up into
clutter once a stock had more than a few, so it was removed. Dots carry no text and the popup shows the
content only on demand, so the line stays readable however many there are. Undated annotations appear in
the card only.

**Baskets.** The sidebar lists baskets and creates or deletes them. With a basket active, the grid gains
a ★ column: clicking ☆ adds that stock, ★ removes it. A toggle switches the grid between **Members only**
and **All stocks** (members starred); an empty basket always shows all stocks, and starring from the full
list keeps it there. A search box in the sidebar (ticker or company name) is a shortcut for adding a
known stock, and members' target quantities are edited inline.

**Portfolio panel.** Once every member of the active basket has a quantity, the bottom panel gains a
**Stocks / Portfolio** switch and opens on the portfolio, showing: market value; today's change in
dollars and percent; return over the selected range; annualised volatility (standard deviation of
daily returns × √252); maximum drawdown (largest fall from a running peak in value); and the best and
worst day. The chart switches between value, daily returns (green/red bars) and cumulative return, with
the same range buttons as the price chart. A holdings table lists each stock's quantity, last price,
market value, weight and today's move, plus its **contribution** to today's portfolio return
(quantity × the stock's dollar move ÷ yesterday's portfolio value, so contributions sum to the
portfolio's daily return). Everything is computed in the browser from the returns endpoint and the
grid's latest closes, so no backend change was needed. The first version was a small cumulative-return
line in the sidebar; it was moved below the grid because the sidebar had no room for the figures and
holdings that make a portfolio view useful.

How stocks get into a basket went through three versions. First, select grid rows and click "Add
selected": a new basket is empty, so filtering the grid to it hid every row and left nothing to select.
Second, a search box only: it worked, but added one stock at a time and couldn't use the grid. The star
column keeps adding in the grid, one click per stock, and stays separate from row selection, which is
capped at five for chart comparison; a star click deliberately doesn't select the row or change the
chart.

**Running it.** `npm run dev` in `frontend/` for local work, and a `web` service in docker-compose so
`docker compose up` starts the whole stack. Frontend tests are out of scope for now.

### Testing, CI and self-evaluation
Tests concentrate on the logic most likely to be silently wrong: reference-data versioning and change
detection (including ticker renames and reuse), price versioning (unchanged bars aren't stored again;
a split adds new versions and keeps the old ones), the startup top-up and nightly refresh jobs, daily
and portfolio return calculations, and detecting missing price dates. The Polygon client is tested against fixture responses,
so the suite never calls the live API, and API tests run against a test Postgres. GitHub Actions runs
linting and type checks (ruff and mypy) and the test suite on every push, checks that migrations match
the models, and fails if the committed OpenAPI spec is out of date. The test suite is the primary
measure of correctness; frontend tests are a next step.

### Keeping the API key out of logs
The Polygon key is sent as an `Authorization: Bearer` header rather than an `apiKey=` URL parameter, and
the HTTP client's request logging is turned down. The first version used the URL parameter, and since
the client logs every request URL, the key was written to job and container logs. A test now checks the
key never appears in a request URL.

### When Polygon fails
The API always answers from Postgres, never directly from Polygon, and grid rows carry the date of the
last stored close. If Polygon is unavailable, on-the-fly gap filling logs a warning and returns what is
stored, and a failed ETL step is recorded in `job_run` and retried on the next scheduled run, so an
outage delays fresh data but never breaks the screen.

## What I'd do next
- **Coverage:** let users add any ticker (fetched on the fly); grow to the S&P 500 or beyond on a paid
  data tier; track dated index membership.
- **Data:** live prices (a display-only delayed quote from a free source such as yfinance, or a paid
  Polygon plan with intraday data), and a second source as a price backup, at which point rows should
  record their `source` again; SEC CIKs to link filings for company research.
- **Data model:** add a raw-payload landing table for replay and lineage; move to full bitemporal history
  (e.g. from Polygon's ticker-change events); add GICS sectors; keep basket membership history; store raw
  prices and dividends for total-return analytics.
- **Product:** a screen-wide "as of" date picker; saved screens; real
  authentication and per-user workspaces.
- **Infrastructure:** an advisory lock so only one ETL job runs at a time; Redis plus Celery for a shared cache and background fetch queue once there are
  multiple API workers; Airflow or Dagster once there are many interdependent jobs; deploy with a hosted
  Postgres; frontend tests.
- **Platform:** treat the instrument master (identity, reference data, prices) as a shared service that
  portfolio, risk, company-research and corporate-access applications build on, each owning its own data
  and reading instruments by UUID.
